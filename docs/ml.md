# ML и LLM

## Разделение ответственности

Система не передаёт одной вероятностной модели несовместимые задачи. Правила распознают безусловные ограничения: PII, финансовый, security, privacy и legal risk, недоступность policy, governance статьи и запрещённые обещания. Они должны быть детерминированными, версионируемыми и fail-closed. Классический дискриминативный классификатор определяет тему тикета и confidence. Retrieval ищет доказуемый контекст, а LLM только переформулирует уже найденную инструкцию.

LLM намеренно отсутствует в горячем routing-пути. TF-IDF и Logistic Regression быстрее, дешевле, стабильнее, воспроизводимы офлайн и допускают явную калибровку порога. LLM запрещена для policy-решений, финансовых и security-действий: она не подтверждает возврат, не блокирует аккаунт, не меняет подписку и не выбирает, допустим ли auto-response. Даже в fulfillment она создаёт только draft, после чего независимый validator проверяет citation, governance и safety. Исходный `Ticket.text` недоступен генератору по типу; передаётся только `SanitizedTicket.redacted_text`.

## Baseline и развитие

PoC использует word TF-IDF с уни- и биграммами и Logistic Regression. Это разумный baseline для малого набора: его легко обучить без GPU, объяснить через признаки, проверить на leakage и откатить по версии. Ограничения ожидаемы: формы русских слов, опечатки и новые формулировки быстро снижают confidence; 55 обучающих строк не дают продуктовой калибровки.

Следующий шаг после накопления разметки — сравнить baseline с multilingual encoder на временном holdout. Encoder должен использоваться для признаков или retrieval, а не получать право принимать policy. При достаточном выигрыше большую модель можно дистиллировать в компактную, измеряя latency и recall риска. Иерархическая схема сначала отделит risk/non-risk, затем уточнит тему; это позволяет отдельно оптимизировать опасные ошибки. Усложнение принимается только при статистически устойчивом выигрыше и сохранении fail-closed маршрута.

В PoC retrieval лексический: заголовок статьи имеет повышенный вес, cosine score дополняется мягким `TOPIC_BOOST = 1.15`. Target hybrid retrieval объединит BM25 или TF-IDF и dense multilingual embeddings, затем выполнит лёгкий rerank. Dense-поиск полезен для семантических перефразирований, но не заменяет фильтры публикации, owner и expiry.

Тема — мягкий буст, а не жёсткий фильтр. Каскад `classifier → retrieval` иначе усиливает первую ошибку: ошибочно предсказанный `PAYMENT` навсегда исключил бы текстово релевантную статью `TECHNICAL`. При boost правильная тема помогает ранжированию, но сильное текстовое совпадение всё ещё может победить. Диагностические `doc_topics` и `topic_match` позволяют увидеть такие каскадные ошибки.

## Валидация и текущие результаты

[Offline-отчёт](eval_report.md) обучает модель только на `tickets_train.jsonl` и оценивает только на непересекающемся `tickets_eval.jsonl`; demo не участвует в обучении или выборе порога. На примерно 20 синтетических примерах получены macro-F1 `0.062`, доля `UNKNOWN` `95%` и Recall@3 `1.000` на десяти ручных retrieval-парах. Recall каждого high-risk класса равен `0.000` при текущем пороге. Эти числа — smoke, а не оценка production quality: выборка слишком мала, доверительный интервал шире различий между разумными вариантами.

Accuracy не является главной метрикой при перекосе классов: частый HOWTO может скрыть пропуск редкого SECURITY. Отчёт поэтому показывает macro-F1, precision и recall каждого класса, отдельно recall `PAYMENT`, `REFUND`, `PRIVACY`, `SECURITY`, UNKNOWN, low-confidence и p95 latency. Для риска recall важнее среднего F1: пропущенный финансовый тикет может получить небезопасную автоматизацию, тогда как лишняя эскалация лишь увеличивает работу оператора. Нулевой текущий recall high-risk означает, что PoC корректно закрывает случаи в `UNKNOWN`, но классификатор ещё нельзя считать готовым для продуктовой маршрутизации.

Retrieval проверяется Recall@3 по ручным парам запрос → документ. Перед production нужны также nDCG, доля запросов без надёжного контекста, governance rejection rate и ручная оценка groundedness. Проверка генерации отдельно измеряет citation correctness, hallucination и unsafe promise rate; красивый текст не компенсирует неверный источник.

## Пороги, low-confidence и UNKNOWN

Порог классификации `CONF_THRESHOLD = 0.65`, relevance `RELEVANCE_THRESHOLD = 0.35`, лимит ответа `MAX_ANSWER_CHARS = 1200`; единственный источник этих значений — `config.py`. Retrieval лишь возвращает честный `max_score` и использованный порог для диагностики. Pipeline решает, достаточно ли score, а validator единолично решает право на auto-response.

Пороги выбираются на временном validation split по функции стоимости

`1000 × unsafe_auto + 50 × wrong_route + 5 × лишняя эскалация + 1 × правка оператора`,

а не по максимуму F1. Коэффициенты фиксируют асимметрию вреда и должны пройти согласование с support, security и compliance. Test/eval остаётся закрытым до финального измерения; подбирать на нём `0.65` или `0.35` было бы leakage.

`UNKNOWN` не обучается как класс: он возникает, когда максимальная вероятность ниже `0.65`, и направляется в безопасный путь. Класса `OTHER` нет намеренно. Одновременные OTHER и UNKNOWN создали бы два неразличимых механизма «я не знаю»: неизвестно, модель распознала устойчивую прочую тему или просто не уверена. Новая частая тема сначала анализируется в UNKNOWN-кластерах, затем получает явный класс и размеченные примеры.

## Данные и обратная связь

Исторические тикеты размечаются по фактическому решению оператора, а не по исходной очереди: очередь сама содержит ошибки старой маршрутизации. Для каждого примера нужны текст после privacy-фильтра, итоговая категория, risk type, принятый или исправленный draft, размер diff, причина отклонения, reopen и CSAT. Финансовые и security labels проходят дополнительный review.

Разбиение выполняется по времени и, где возможно, по клиенту или thread, чтобы одинаковые шаблоны диалогов не оказались по обе стороны. KB-текст, ответы операторов и дубликаты тикетов дедуплицируются до split. Версия KB, policy и model сохраняется рядом с прогнозом. Нельзя превращать будущий статус заявки, финальный queue или текст ответа оператора в признаки: это target leakage.

Ground truth часто delayed: категория уточняется после разговора, reopen появляется через дни, CSAT — ещё позже. Label pipeline связывает эти события по `correlation_id`, закрывает окно наблюдения и создаёт immutable snapshot. До созревания labels они не участвуют в обучении. Drift отслеживается по росту UNKNOWN, изменению class mix, confidence и human-edit rate; решение о переобучении принимает человек после анализа причин, а не автоматический триггер.
