# ML и LLM

> **Audience: For AI**

## Разделение ответственности

Система не передаёт одной вероятностной модели несовместимые задачи. Детерминированная policy распознаёт финансовый, security, privacy и legal risk, низкую уверенность и собственную недоступность; найденный тип карты также включает финансовое правило. Governance статьи (`auto_allowed`, публикация, owner и срок действия), PII в готовом тексте и запрещённые обещания независимо проверяет validator. Оба слоя работают fail-closed. Классический дискриминативный классификатор определяет тему тикета и confidence, retrieval ищет доказуемый контекст, а LLM только переформулирует найденную инструкцию.

LLM намеренно отсутствует в горячем routing-пути. TF-IDF и Logistic Regression быстрее, дешевле, стабильнее и воспроизводимы офлайн; текущий `confidence` — максимальная `predict_proba`, а не калиброванная вероятность. LLM запрещена для policy-решений, финансовых и security-действий: она не подтверждает возврат, не блокирует аккаунт, не меняет подписку и не выбирает, допустим ли auto-response. В fulfillment она создаёт только draft, после чего независимый validator проверяет citation, governance и safety. При отказе LLM строится детерминированный шаблон, но деградированный ответ отправляется только оператору. Исходный `Ticket.text` недоступен генератору по типу; передаётся только ограниченный по длине и очищенный `SanitizedTicket.redacted_text`.

## Baseline и развитие

PoC использует word TF-IDF с уни- и биграммами и Logistic Regression. Это разумный baseline для малого набора: его легко обучить без GPU, объяснить через признаки, проверить на leakage и откатить по версии. Ограничения ожидаемы: формы русских слов, опечатки и новые формулировки быстро снижают confidence; 75 обучающих строк не дают продуктовой калибровки.

Следующий шаг после накопления разметки — сравнить baseline с multilingual encoder на временном holdout. Encoder должен использоваться для признаков или retrieval, а не получать право принимать policy. При достаточном выигрыше большую модель можно дистиллировать в компактную, измеряя latency и recall риска. Иерархическая схема сначала отделит risk/non-risk, затем уточнит тему; это позволяет отдельно оптимизировать опасные ошибки. Усложнение принимается только при статистически устойчивом выигрыше и сохранении fail-closed маршрута.

В PoC retrieval лексический: заголовок статьи повторяется трижды в индексируемом тексте, а cosine score дополняется мягким `TOPIC_BOOST = 1.15`. Поиск возвращает до пяти статей и их governance-метаданные, но ничего не отфильтровывает по публикации, owner или сроку: право на автоответ проверяется позже validator-ом. Target hybrid retrieval объединит BM25 или TF-IDF и dense multilingual embeddings, затем выполнит лёгкий rerank. Dense-поиск полезен для семантических перефразирований, но не заменяет governance-проверки.

Тема — мягкий буст, а не жёсткий фильтр. Каскад `classifier → retrieval` иначе усиливает первую ошибку: ошибочно предсказанный `PAYMENT` навсегда исключил бы текстово релевантную статью `TECHNICAL`. При boost правильная тема помогает ранжированию, но сильное текстовое совпадение всё ещё может победить. Диагностические `doc_topics` и `topic_match` позволяют увидеть такие каскадные ошибки.

## Валидация и текущие результаты

[Offline-отчёт](eval_report.md) обучает модель только на `tickets_train.jsonl` и оценивает на отдельном `tickets_eval.jsonl`; demo не участвует в обучении или выборе порога. Однако eval использовался как development/validation set для настройки порога и policy, поэтому независимым test-набором не является. На 20 синтетических примерах при текущем config получены macro-F1 `0.933`, доля `UNKNOWN` `0%`, model recall high-risk macro `0.875`, policy recall high-risk с корректным `risk_type` `1.000` и Recall@3 `1.000` на десяти ручных retrieval-парах. Эти числа — smoke, а не оценка production quality: выборка слишком мала и на ней велась настройка.

Accuracy не является главной метрикой при перекосе классов: частый HOWTO может скрыть пропуск редкого SECURITY. Отчёт поэтому показывает macro-F1, precision и recall каждого класса, отдельно recall `PAYMENT`, `REFUND`, `PRIVACY`, `SECURITY`, UNKNOWN, low-confidence и p95 latency. Для риска recall важнее среднего F1: пропущенный финансовый тикет может получить небезопасную автоматизацию, тогда как лишняя эскалация лишь увеличивает работу оператора. Policy-level recall отдельно проверяет не только `ESCALATE`, но и корректный `risk_type`; он может быть выше model recall благодаря детерминированным ключевым словам. Даже текущие значения не делают классификатор готовым для продуктовой маршрутизации: набор мал и не является независимым test.

Retrieval проверяется Recall@3 по ручным парам запрос → документ. Перед production нужны также nDCG, доля запросов без надёжного контекста, governance rejection rate и ручная оценка groundedness. Проверка генерации отдельно измеряет citation correctness, hallucination и unsafe promise rate; красивый текст не компенсирует неверный источник.

## Пороги, low-confidence и UNKNOWN

Порог классификации `CONF_THRESHOLD = 0.30`, relevance `RELEVANCE_THRESHOLD = 0.35`, лимит ответа `MAX_ANSWER_CHARS = 1200`; единственный runtime-источник этих значений — `config.py`. Retrieval лишь возвращает `max_score` и использованный порог для диагностики. Pipeline решает, достаточно ли score, а validator окончательно решает право на auto-response.

Текущий порог выбран свипом `0.30–0.70` на development/eval-наборе по функции стоимости

`1000 × unsafe_auto + 50 × wrong_route + 5 × лишняя эскалация + 1 × правка оператора`,

а не по максимуму F1. Коэффициенты фиксируют асимметрию вреда и должны пройти согласование с support, security и compliance. Для честного финального измерения нужен новый закрытый test-набор: текущий `tickets_eval.jsonl` уже участвовал в выборе `0.30` и не может выполнять эту роль.

`UNKNOWN` не обучается как класс: он возникает, когда максимальная вероятность ниже `0.30`, и направляется в безопасный путь. Класса `OTHER` нет намеренно. Одновременные OTHER и UNKNOWN создали бы два неразличимых механизма «я не знаю»: неизвестно, модель распознала устойчивую прочую тему или просто не уверена. Новая частая тема сначала анализируется в UNKNOWN-кластерах, затем получает явный класс и размеченные примеры.

До классификации `normalize` удаляет HTML, обрывает цитируемую переписку и подпись по поддерживаемым маркерам, декодирует HTML entities и схлопывает пробелы. Затем PII маскируется. Policy получает полный нормализованный и маскированный текст, поэтому ограничение длины нельзя использовать для обхода risk-правил; классификатор, retrieval и generator получают его версию не длиннее `MAX_TICKET_CHARS`.

## Данные и обратная связь

Исторические тикеты размечаются по фактическому решению оператора, а не по исходной очереди: очередь сама содержит ошибки старой маршрутизации. Для каждого примера нужны текст после privacy-фильтра, итоговая категория, risk type, принятый или исправленный draft, размер diff, причина отклонения, reopen и CSAT. Финансовые и security labels проходят дополнительный review.

Разбиение выполняется по времени и, где возможно, по клиенту или thread, чтобы одинаковые шаблоны диалогов не оказались по обе стороны. KB-текст, ответы операторов и дубликаты тикетов дедуплицируются до split. Версия KB, policy и model сохраняется рядом с прогнозом. Нельзя превращать будущий статус заявки, финальный queue или текст ответа оператора в признаки: это target leakage.

Ground truth часто delayed: категория уточняется после разговора, reopen появляется через дни, CSAT — ещё позже. Label pipeline связывает эти события по `correlation_id`, закрывает окно наблюдения и создаёт immutable snapshot. До созревания labels они не участвуют в обучении. Drift отслеживается по росту UNKNOWN, изменению class mix, confidence и human-edit rate; решение о переобучении принимает человек после анализа причин, а не автоматический триггер.
